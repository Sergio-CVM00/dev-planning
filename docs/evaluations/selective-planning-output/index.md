## Destination and outcome

Boardroom owners currently request membership changes through support. The outcome is that a signed-in team owner creates a durable, 24-hour invitation link only for an email whose normalized domain exactly matches the team's configured allowed domain, including an eligible target with no account or an existing membership; a team without that configuration rejects creation. Repeat requests for the same eligible email await D-07's reject/reuse/new-token decision. A signed-in matching account without existing membership accepts an eligible link once only if the current team domain policy permits it, including after a reload or server restart when no prior policy rejection has changed its eligibility. Already-member acceptance and acceptance eligibility of any other issued invitation await D-06. Team boards remain invisible to nonmembers. The granted member role is the saved plan's pending D-02 proposal; policy-rejected token fate is pending D-05.

IN: invitation creation, link sharing by people, signed-in acceptance, current allowed-domain checks, persisted state, expiration, single-use consumption, concurrent acceptance safety, client states, server authorization, and tenant isolation. OUT: allowed-domain configuration, email delivery, reminders, billing, production deployment, and an orchestration framework. Do not infer invitation revocation, owner-role grants, or broader membership administration from this slice.

Planning depth: **Standard, with deep treatment of authorization and token use**. This is an existing product feature crossing client, API, persistence, and a new bearer-link trust boundary. [Product and system impact](product-system.md) and the [delivery roadmap](roadmap.md) retain the global destination.
