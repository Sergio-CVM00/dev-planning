# Product frame and system impact

Source and revision: [project.md](../../evaluation-fixtures/team-invitations/project.md), supplied 2026-10-11. All claims of current behavior below come from that fixture; no running product or code is available for corroboration.

## Product frame

- Actors: a signed-in team owner who may create, a member or nonmember who may not create, a signed-in account matching the target email that may accept, and an unauthenticated or different account that may not accept.
- Current need: owners request membership changes through support. The feature lets an authorized sender share a link themselves and lets the target account join without support. Frequency, support cost, and adoption targets are unknown and are not needed to choose the first bounded slice.
- Observable outcome: a current owner can create a link only for a valid email whose normalized domain exactly matches the team's current configured allowed domain, including one without an account or already in the team; repeated creation for the same eligible email is allowed. A team without an allowed domain rejects creation. A matching signed-in account without existing membership can accept after a reload or restart before expiry when the current allowed domain matches and the link has not previously met a policy-rejection state whose fate awaits [D-05](decisions.md#d-05---rejected-invitation-token-lifecycle). The already-member result and eligibility of repeat invitations await [D-06](decisions.md#d-06---already-member-acceptance-and-repeat-invitations). At most one membership row results, while nonmembers never see board data. Success evidence is planned API integration and web journey results, not a numerical adoption target.
- Scope and constraints: see [index](index.md). Allowed-domain configuration is an existing team input outside this slice. A new invitation grants the existing member role only in the proposed slice; owner transfer and role selection are outside its boundary. This is a scoped proposal, not a confirmed product policy.

## Existing system and affected path

```text
Signed-in web client -> authenticated HTTP interface -> server authorization/domain handling
                                                       -> PostgreSQL users, teams, memberships
                                                       -> proposed invitations table
```

The signed-in client has a selected team. The server receives identity and selected team but must derive authorization from persisted membership and enforce it server-side. Membership uniqueness is `(team_id, user_id)`. Invitation links are externally shareable, so token possession enters through a new trust boundary. The server must still require signed-in identity and target-email match. PostgreSQL owns invitation lifecycle and membership state so both survive process restart. There is no email provider or background job in this slice.

The creation boundary checks the sender's current owner role, validates target email syntax without requiring a target account or checking target membership, reads the selected team's authoritative allowed domain, and requires an exact normalized domain match before inserting the invitation and returning a URL. Missing configuration rejects creation; repeated eligible creation produces distinct tokens. The acceptance boundary touches authentication, token lookup, the current team allowed domain, authoritative account-email comparison, atomic consumption for a new-member success, and membership insert. A legacy unused invitation for a different domain cannot grant access. Existing board reads must keep their server-side membership check; accepting a link cannot reveal boards to a nonmember before membership commit. The client must treat link and error responses as sensitive and avoid putting board data in invitation preview states.

## System proposal and consequences

Use an opaque high-entropy random token in the shared link, store only its cryptographic digest, and persist team ID, canonical target email, creator ID, creation/expiry timestamps, consumption timestamp, and consuming user ID. The invitation table is the source of truth. The token must not appear in logs, analytics, or outbound referrer data. Exact field names, URL shape, response status codes, and migration tooling follow the existing repository after [U-01](decisions.md#u-01---actual-contract-and-repository) is resolved. No background expiry job is needed: compare against server time at read and acceptance; retain expired rows until a later retention policy is chosen.

Acceptance should run in one database transaction that locks the invitation row, confirms a valid token and unexpired state, reads the current team allowed domain under a serialization strategy compatible with domain updates, requires its exact normalized match with the stored target-email domain, and compares the current signed-in account email with the target under existing account semantics. For a matching account without membership, it inserts one membership subject to the existing unique constraint and marks the successful invitation consumed. Missing or mismatched domain rejects without changing membership; [D-05](decisions.md#d-05---rejected-invitation-token-lifecycle) must settle whether that rejection invalidates the token or leaves it pending for later policy changes. The rejection write, state model, and recovery response remain provisional. Member-role insertion is provisional until [D-02](decisions.md#d-02---member-role-target-for-s-01) is confirmed. A matching account already in the team cannot gain a duplicate membership row; [D-06](decisions.md#d-06---already-member-acceptance-and-repeat-invitations) must settle the response, any role effect, presented-token state, and later-invitation eligibility. Competing new-member accepts must yield exactly one successful consumption; the loser receives a stable used/ineligible result. A failed transaction leaves an otherwise eligible invitation usable if still within 24 hours. A lost HTTP response after committed new-member acceptance does not create another membership on retry.

This uses the existing HTTP/PostgreSQL architecture and avoids a new queue, provider, or orchestration framework. A relational transaction is necessary because consumption and membership are one domain event. If the actual repository has different identity, allowed-domain, or transaction semantics, U-01 may require a revised plan before building.
