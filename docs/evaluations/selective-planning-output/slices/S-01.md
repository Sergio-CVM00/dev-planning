# S-01 - Create and accept a member invitation

Revision: 2026-10-11, repaired after independent already-member lifecycle finding. The member-role grant awaits D-02; lifecycle after policy rejection awaits D-05; already-member acceptance and repeat-invitation consequences await D-06. ## Objective and boundary

A signed-in owner of the selected team creates a 24-hour, shareable invitation only for a valid target email whose normalized domain exactly matches the team's current configured allowed domain, including one without an account or already in the team. Repeated creation for the same eligible email is allowed. A team without that configuration rejects creation. Only a signed-in account matching the email may attempt acceptance, and an unused invitation is rejected if its target domain no longer matches the current team policy. The token's fate after that rejection awaits D-05. The proposed grant is one member-role membership when the account is not already a member, pending D-02. Already-member acceptance, presented-token fate, and later-invitation eligibility await D-06. The invitation persists after reload and process restart; acceptance remains subject to expiry, current domain policy, and the eventual D-05/D-06 lifecycle rules. A committed membership persists under normal membership rules. People share links themselves. Allowed-domain configuration, email service, reminders, owner-role grants, invitation list/revocation UI, billing, and production deployment are outside S-01.

## Proposed flow and contracts

1. The selected-team membership page exposes an invite action to current owners. Enter a valid target email; submit through the existing authenticated request boundary. Show loading/disabled submission, syntax/domain validation, missing-domain configuration guidance for the owner, permission error, and a success view with link, copy action, and 24-hour expiry. The configuration guidance does not add a configuration flow. Use the existing design system, responsive layout, keyboard focus and announcements for error/success. The UI guards accidental double submission; an explicit retry of creation may make a separate invitation because the server stores only the token digest and cannot return a lost raw link.
2. Creation input is selected team identity and target email. The server gets sender identity from authentication, validates and canonicalizes email syntax under existing account semantics, checks current owner permission, reads the authoritative current team allowed domain, and requires exact equality of normalized domains before generating a cryptographically strong opaque token, storing its digest and invitation metadata, and returning the raw link once. An absent allowed domain denies creation. A domain such as a subdomain or suffix lookalike is unequal unless it is the configured domain itself. It does not require a target account, reject an existing member, or reveal whether the email has an account or membership. Repeated creation for the same eligible email may produce distinct invitations. Proposed share URL holds the token in a fragment; the client submits it through an authenticated acceptance request. No invitation record grants access itself.
3. Opening the link shows a generic state until signed in. The client preserves the link across the sign-in flow without exposing the token through external referrers. A signed-in visitor may choose Accept; no team name, board title, or member list is fetched for the preview. Wrong-account and expired/used outcomes are distinct enough to guide recovery without exposing target email to unrelated accounts. If no account existed at creation, a matching account must exist and be signed in by acceptance time. Account registration itself is outside this slice. The target may sign into the correct account or request a new link through the sender. Guidance after a domain-policy rejection awaits D-05; already-member and repeat-invitation guidance awaits D-06. Neither may promise unconfirmed retry eligibility.
4. Acceptance input is token only; identity and current email come from the authenticated account. The server compares a digest lookup, current time, valid state, and authoritative account email under U-01 semantics. Within the acceptance transaction it rechecks the authoritative current team allowed domain against the stored target-email domain and serializes that check with concurrent domain updates before any membership insert or successful token consumption. An absent or mismatched allowed domain rejects an unused invitation without a membership change; D-05 determines any token-state write and later eligibility. The response is privacy-preserving and offers generic recovery guidance without team-private data. For a matching account without existing membership, it inserts the D-02 grant membership subject to `(team_id, user_id)` uniqueness and consumes the invitation in the same PostgreSQL transaction. The already-member branch requires D-06 before specifying its response, token write, or later-invitation eligibility; the unique constraint still bars duplicate rows. Invalid/expired/used/wrong-account/domain-ineligible responses contain no board payload. After a new-member success, navigate into the team using existing membership-gated access.

The confirmed state needs `pending`, `consumed` on successful new-member acceptance, and expiry computed from timestamps. D-05 may add a terminal invalidated state or retain pending state after policy rejection; D-06 determines any state transition on already-member acceptance and the eligibility of repeat invitations. The state model and corresponding schema are provisional until those choices. Persist at least invitation ID, team ID, target canonical email, token digest (unique index), creator user ID, created/expires timestamps, consumed timestamp, and consuming user ID where applicable, with additional state fields determined by D-05/D-06. Use server time for the 24-hour boundary. No background job is needed. PostgreSQL is the state owner; never rely on process memory or client state for token status. A schema migration adds the table without modifying existing memberships; on code rollback, preserve the table and pending links until a deliberate compatibility/recovery decision. Exact schema and route names depend on U-01.
