# S-01 - Create and accept a member invitation

Revision: 2026-10-11, repaired after separate plan-review feedback. Sources: [project.md](../../../evaluation-fixtures/team-invitations/project.md), [product/system impact](../product-system.md), [decision records](../decisions.md). D-01 owner-only creation, D-03 matching signed-in acceptance, and D-04 current allowed-domain eligibility are confirmed; D-04 supersedes D-03's any-email eligibility. The member-role grant awaits D-02; the lifecycle after policy rejection awaits D-05. Exact HTTP paths, field names, domain normalization, and account-email comparison semantics require U-01.

## Objective and boundary

A signed-in owner of the selected team creates a 24-hour, shareable invitation only for a valid target email whose normalized domain exactly matches the team's current configured allowed domain, including one without an account or already in the team. A team without that configuration rejects creation. Only a signed-in account matching the email may accept, and an unused invitation is rejected if its target domain no longer matches the current team policy. The token's fate after that rejection awaits D-05. The proposed grant is one member-role membership when the account is not already a member, pending D-02. The invitation persists after reload and process restart; acceptance remains subject to expiry, current domain policy, and the eventual D-05 lifecycle rule. A committed membership persists under normal membership rules. People share links themselves. Allowed-domain configuration, email service, reminders, owner-role grants, invitation list/revocation UI, billing, and production deployment are outside S-01.

## Proposed flow and contracts

1. The selected-team membership page exposes an invite action to current owners. Enter a valid target email; submit through the existing authenticated request boundary. Show loading/disabled submission, syntax/domain validation, missing-domain configuration guidance for the owner, permission error, and a success view with link, copy action, and 24-hour expiry. The configuration guidance does not add a configuration flow. Use the existing design system, responsive layout, keyboard focus and announcements for error/success. The UI guards accidental double submission; an explicit retry of creation may make a separate invitation because the server stores only the token digest and cannot return a lost raw link.
2. Creation input is selected team identity and target email. The server gets sender identity from authentication, validates and canonicalizes email syntax under existing account semantics, checks current owner permission, reads the authoritative current team allowed domain, and requires exact equality of normalized domains before generating a cryptographically strong opaque token, storing its digest and invitation metadata, and returning the raw link once. An absent allowed domain denies creation. A domain such as a subdomain or suffix lookalike is unequal unless it is the configured domain itself. It does not require a target account, reject an existing member, or reveal whether the email has an account or membership. Repeated creation for the same eligible email may produce distinct invitations. Proposed share URL holds the token in a fragment; the client submits it through an authenticated acceptance request. No invitation record grants access itself.
3. Opening the link shows a generic state until signed in. The client preserves the link across the sign-in flow without exposing the token through external referrers. A signed-in visitor may choose Accept; no team name, board title, or member list is fetched for the preview. Wrong-account and expired/used outcomes are distinct enough to guide recovery without exposing target email to unrelated accounts. If no account existed at creation, a matching account must exist and be signed in by acceptance time. Account registration itself is outside this slice. The target may sign into the correct account or request a new link through the sender. Guidance after a domain-policy rejection must await D-05 and must not promise that the same link will work later.
4. Acceptance input is token only; identity and current email come from the authenticated account. The server compares a digest lookup, current time, valid state, and authoritative account email under U-01 semantics. Within the acceptance transaction it rechecks the authoritative current team allowed domain against the stored target-email domain and serializes that check with concurrent domain updates before any membership insert or successful token consumption. An absent or mismatched allowed domain rejects an unused invitation without membership; D-05 determines any token-state write and later eligibility. The response is privacy-preserving and offers generic recovery guidance without team-private data. If eligible, it inserts the D-02 grant membership subject to `(team_id, user_id)` uniqueness and consumes the invitation in the same PostgreSQL transaction. An existing membership is not changed. It returns success or a stable invalid/expired/used/wrong-account/domain-ineligible/already-member outcome without board payload, with policy-rejected recovery mapping finalized after D-05. After success, navigate into the team using existing membership-gated access.

The confirmed state needs `pending`, `consumed` on successful acceptance, and expiry computed from timestamps. D-05 may add a terminal invalidated state or retain pending state after policy rejection; the state model and corresponding schema are provisional until that choice. Persist at least invitation ID, team ID, target canonical email, token digest (unique index), creator user ID, created/expires timestamps, consumed timestamp, and consuming user ID, with any rejection-state fields determined by D-05. Use server time for the 24-hour boundary. No background job is needed. PostgreSQL is the state owner; never rely on process memory or client state for token status. A schema migration adds the table without modifying existing memberships; on code rollback, preserve the table and pending links until a deliberate compatibility/recovery decision. Exact schema and route names depend on U-01.

Required fixtures are two teams with configured and missing allowed domains, an adjustable team domain for policy-change cases, owners, members, a signed-in nonmember, a matching target account, a wrong account, an unused invitation created under a previous domain, and controllable server time or a time fixture. U-01 must establish configuration and normalization semantics; U-02 tracks harness access; U-03 tracks the registered product execution host. AC-12's token-state and later-policy-change assertions remain open until D-05.
