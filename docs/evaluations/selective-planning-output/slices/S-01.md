# S-01 - Create and accept a member invitation

Revision: 2026-10-11, reconciled with the user's allowed-domain update. Sources: [project.md](../../../evaluation-fixtures/team-invitations/project.md), [product/system impact](../product-system.md), [decision records](../decisions.md). D-01 owner-only creation, the surviving D-03 account/membership and identity rules, and D-04 team-domain policy are confirmed. The member-role grant is provisional pending D-02. Exact HTTP paths, field names, account-email comparison, and domain normalization semantics require U-01.

## Objective and boundary

A signed-in owner of the selected team creates a 24-hour, shareable invitation only for a valid target email whose normalized domain exactly matches the team's configured allowed domain, including an eligible address without an account or already in the team. A team without an allowed domain rejects creation. Only a signed-in account matching that email may accept, and acceptance rechecks the team's current allowed domain so unused older links to another domain cannot grant access. The proposed grant is one member-role membership when the account is not already a member, pending D-02. The invitation and resulting membership remain valid after reload and process restart. People share links themselves. Domain configuration, email service, reminders, owner-role grants, invitation list/revocation UI, billing, and production deployment are outside S-01.

## Proposed flow and contracts

1. The selected-team membership page exposes an invite action to current owners. Enter a valid target email; submit through the existing authenticated request boundary. Show loading/disabled submission, validation error, missing-domain or disallowed-domain error, permission error, and a success view with link, copy action, and 24-hour expiry. Missing configuration guidance may direct the owner to an existing configuration path if one exists; building configuration is outside this slice. Use the existing design system, responsive layout, keyboard focus and announcements for error/success. The UI guards accidental double submission; an explicit retry of creation may make a separate invitation because the server stores only the token digest and cannot return a lost raw link.
2. Creation input is selected team identity and target email. The server gets sender identity from authentication, validates and canonicalizes email syntax under existing account semantics, checks current owner permission, reads the team's authoritative current allowed domain, and requires an exact match of normalized domains. If the setting is absent or the domains differ, it returns a stable denial and stores no invitation. If eligible, it generates a cryptographically strong opaque token, stores its digest and invitation metadata, and returns the raw link once. It does not require a target account, reject an existing member, or reveal whether the email has an account or membership. Repeated creation for the same eligible email may produce distinct invitations. Proposed share URL holds the token in a fragment; the client submits it through an authenticated acceptance request. No invitation record grants access itself.
3. Opening the link shows a generic state until signed in. The client preserves the link across the sign-in flow without exposing the token through external referrers. A signed-in visitor may choose Accept; no team name, board title, or member list is fetched for the preview. Wrong-account, domain-policy rejection, and expired/used outcomes guide recovery without exposing target email or configured domain to unrelated accounts. If no account existed at creation, a matching account must exist and be signed in by acceptance time. Account registration and team-domain configuration are outside this slice. The target may sign into the correct account or request a new eligible link through the sender.
4. Acceptance input is token only; identity and current email come from the authenticated account. The server compares a digest lookup, current time, consumed state, and authoritative account email under U-01 semantics. It also reads the invitation team's current allowed domain and requires an exact normalized match to the stored target email's domain, including for unused invitations created before this rule or before a domain change. A missing or different domain returns a privacy-preserving policy denial without consuming the link or inserting membership. The check and grant must share a consistency boundary so a concurrent domain change cannot authorize an ineligible acceptance; U-01 determines the concrete mechanism. If eligible, the server locks/serializes the invitation, inserts the D-02 grant membership subject to `(team_id, user_id)` uniqueness, and consumes the invitation in one PostgreSQL transaction. An existing membership is not changed. It returns success or a stable invalid/expired/used/wrong-account/domain-policy/already-member outcome without board payload. After success, navigate into the team using existing membership-gated access.

Invitation state is `pending`, `consumed`, or `expired` as computed from timestamps. Domain-policy eligibility is a separate current check, not a persisted terminal invitation state. Persist at least invitation ID, team ID, target canonical email, token digest (unique index), creator user ID, created/expires timestamps, consumed timestamp, and consuming user ID. Use server time for the 24-hour boundary. No background job is needed. PostgreSQL is the invitation state owner; the existing authoritative team configuration owns the allowed domain. Never rely on process memory or client state for token or policy status. A schema migration adds the invitation table without modifying existing memberships or creating a domain configuration interface; on code rollback, preserve the table and pending links until a deliberate compatibility/recovery decision. Exact schema, setting location, normalization, and route names depend on U-01.
